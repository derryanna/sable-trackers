## Коротко (ru)

- **Паки** (§15): наборы секций и правил под тип сцены (бой, интим), включаются
  в чате кнопкой 🎒, по умолчанию выключены. Свои паки, копия встроенного,
  переопределения в «опасной зоне», переключатель «кого считать: всех / только
  меня», локальный кубик d100 без модели.
- **Живые карточки** (§16): уровень эффектов off / subtle / full вместо запрета
  на анимацию. Полоски едут, изменения подсвечиваются, в full тикают цифры,
  полоска краснеет, кубик крутится.
- **Баг** (T10): после трёх новых свайпов одного ответа кольцо теряет состояние
  «до» него, четвёртый свайп идёт без инжекта, трекеры собираются заново.
  Воспроизведено скриптом. Отдельно: настройка роли инжекта (system / user /
  assistant) для моделей, которые копируют блок состояния в ответ.
- **Порядок**: T10 → T8a → T8b → T8c → T9. Открытые вопросы в конце.

## 1. What the maintainer asked for

1. "Packs" for the interface: switch on a bundle for a fight, an intimate scene
   and so on, with playful stats (HP, crit chance, counters such as volume in
   ml). Confirmed: packs must be editable and the user must be able to build
   their own.
2. Visuals: the maintainer does not want the extension to feel heavy, **but**
   the repository is public and taste differs, so richer motion must exist as
   an option for everyone, not be ruled out.
3. Combat stats: per participant or only the user character → "let the user
   choose" (pack `scope`).
4. Dice button: approved.
5. A bug report: "if I swipe afterwards, Sable's injection also ends up in the
   text; happens rarely; feels like a bug; maybe needs a knob."

## 2. Decisions recorded in SPEC.md

### §15 Packs
- Pack = `{ id, title, icon, description, rules, sections[], scope? }`. Built-in
  ids are slugs (`combat`, `intimacy`), user packs `p_` + 8 hex. Pack section
  id = `${packId}_${key}`; they are custom sections (§11) in every pure
  function, so `getSections(settings, enabledPacks)` is the only new entry
  point the core needs.
- Two new shapes, available to custom sections too: `stats` (bars with `max`,
  counters with `max: null`, `delta` computed in merge, `note` from the model)
  and `tags` (chips).
- Enabled per chat (`chat_metadata.sableTrackers.packs`), with
  `settings.packDefaults` for chats without the key. Off = not requested, not
  shown, not injected; values stay in the ring.
- `pack.rules` appended after the common rules while any pack section is due.
- Export/import `sable-pack.json`, same approach as `src/themes.js`.
- Editing: "Make a copy" turns a built-in into a user pack; built-ins are also
  tunable in place through `prompts.sections[id]` and `prompts.packs[packId]`.
- `scope`: `all` | `user` per pack (`settings.packScope`), `{{scope}}` expanded
  in instructions.
- Dice: a `%` row gets 🎲; d100 rolled locally (`roll(chance, random)`), the
  result written to `<pack>_roll` through `runtime.editState`, so it is injected
  like any manual edit. Nothing else in the extension rolls or decides.
- Built-in content sketched for `combat` and `intimacy`; the intimacy pack keeps
  the adults-only guard from §2 (empty values otherwise). Candidates later:
  investigation, survival, travel.

### §16 Live cards
- `visual.motion` (boolean) becomes `visual.effects`: `off` | `subtle` |
  `full`, migrated on load (`false → off`, `true → subtle`). Reduced-motion
  forces `off`.
- `subtle`: bars slide (`scaleX`, 180 ms, keyed reconcile so the node
  survives), change flash + title dot, tap for the reason/note.
- `full`: number ticks, value-coloured bars with a pulse under 20 %, dice spin
  and crit glow, card glow, animated reply panel.
- Engineering limits that are not a matter of taste: plain DOM, no canvas or
  libraries, no layout animation, nothing on a timer while the user types.

## 3. Bug: the ring forgets the base after three swipes (T10)

**Verified**, deterministic. `putEntry` in `src/store.js` keeps the newest
`settings.keep` (default 3) ring entries **in total**, and each swipe of a
message is its own entry. Repro (node, from the repo root):

```js
import { loadStore, putEntry, currentEntry } from './src/store.js';
const chat = [{is_user:true},{},{is_user:true},{},{is_user:true},{swipe_id:0}];
const data = loadStore({ chatMetadata: {} });
putEntry(data, { mesId: 1, swipeId: 0, turn: 1, state: {} }, 3);
putEntry(data, { mesId: 3, swipeId: 0, turn: 2, state: {} }, 3);
for (let s = 0; s <= 3; s++) {
  chat[5].swipe_id = s;
  console.log(s, currentEntry(data, chat, 5)?.mesId, currentEntry(data, chat)?.mesId);
  putEntry(data, { mesId: 5, swipeId: s, turn: 3, state: {} }, 3);
}
// 0 3 3 · 1 3 3 · 2 3 3 · 3 undefined undefined  ← ring is now 5/1 5/2 5/3
```

Consequences on the fourth new swipe of one reply: `publish()` finds no
current entry, so the injection is **empty** during that generation; the
side-model run then has no base and rebuilds the state from the last four
messages alone. From the chair this looks like the trackers forgetting the
scene. The ring also no longer holds an entry for swipe 0, so swiping back
left triggers a fresh request instead of a restore.

Proposed fix: cap by distinct `mesId` (newest `keep` messages) and cap swipes
per message (6, oldest dropped). `currentEntry` and `findEntry` stay as they
are. Tests: four swipes keep the base and the injection; swipe back restores;
`MESSAGE_DELETED` pruning unchanged. Size: small, one PR.

## 4. What the swipe flow does today (checked against SillyTavern sources)

Fetched `public/script.js` and `public/scripts/openai.js` from the SillyTavern
`release` branch on 2026-10-02 (not stored in the repo). Findings:

- `swipe()` → `loadFromSwipeId` / overswipe branch sets `chat[mesId].swipe_id`
  to the new id **before** `animateSwipe`, which emits `MESSAGE_SWIPED` and
  only then calls `Generate('swipe')`. So `runtime.swipe()` sees the new id,
  `currentEntry` skips the old swipe's entry, and the base state is injected
  for the new generation. By design the discarded swipe's facts do not leak.
- `Generate`: `coreChat.pop()` for `type === 'swipe'`, and chat completion
  builds its history from that, so depth counts from the message before the
  swiped one, the same as on a normal turn.
- Regenerate removes the last message and emits `MESSAGE_DELETED`, which the
  runtime already handles (`deleted()` prunes and re-publishes).

So the only deterministic defect found is the ring eviction above. The
reported "injection ends up in the text" may instead be the **main model
copying the injected block** (system role, depth 2) into its reply, a model
quirk that is rare and not swipe-specific. Mitigation planned in T10: expose
`settings.role` (system / user / assistant) next to depth; some models echo
user-role notes less. Needs the maintainer's answer to the open question below.

## 6. Open questions for the maintainer

1. **Swipe symptom**: does the new swipe contain the literal block
   (`WORLD: … NPCS: …`), or events from the discarded swipe that the model
   should not know? Which main model / API? This decides whether T10's role
   knob is enough or whether something else is going on.
2. **Pack switch placement**: drawer header 🎒 (spec) vs a row of pack chips
   above the cards. Header is cheaper; chips are more visible on a phone.
3. **Intimacy pack naming** in the UI (ru/en) and whether it ships enabled in
   the pack list by default or behind an "18+" tick in settings.
4. **Dice scope**: only `%` rows (spec) or any `stats` row with `max`
   (roll under value)?
5. **`full` effects** wish list: anything specific seen in other trackers that
   should be on it?
